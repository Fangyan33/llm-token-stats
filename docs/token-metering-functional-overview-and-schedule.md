# 大模型用量计量、计费与对账平台功能设计概览及开发周期

日期：2026-10-13｜用途：客户方案评审、建设范围确认与工作量预估

范围修订说明（2026-10-16）：采集及 Consumer 已实现，当前两类归属接口只有未实现占位，不具备真实客户/供应商解析。已删除客户下属应用模型，按客户/API Key、服务/供应商及集群/环境统计。下文人天及排期为原完整产品范围的历史估算，真实接口、鉴权、汇总和计费仍需重新确认工作量，不能把占位交付当完整平台或报价依据。

> 本方案基于现有《LLM 请求用量计量与统计设计》整理，新增计费、账单和对账的产品设计。以下能力为拟建范围，人天为初步估算；实际交付范围与验收指标在需求确认及技术验证后确定。阶段 0 为实施前验证；一期交付鉴权与完整用量统计，二期交付计费、账单发布及调整单，三期交付对账与结算确认。网关请求采集开发方案只细化一期中的“采集到 Doris 明细入库”子项，不能代替一期整体验收。原文保留作为技术设计参考。

## 1. 建设目标

建设统一的模型用量管理平台，让客户能够查清“谁调用了什么模型、用了多少、应收多少、账单是否一致”，形成从请求采集到最终对账的完整流程。

平台提供六类能力：

| 功能模块 | 解决的问题 | 主要交付 |
| --- | --- | --- |
| 接入与归属 | 用量属于哪个客户、哪个服务/供应商 | 客户/API Key 与服务/供应商关联、API Key 归属、服务与模型配置 |
| 用量计量 | 每次请求实际可确认的消耗是多少 | 请求明细、输入/输出用量、来源与完整性标识 |
| 价格与计费 | 按什么规则计算费用 | 价格版本、计费规则、费用明细 |
| 账单管理 | 一个账期应收多少钱 | 账单生成、审核、发布、明细导出及调整单 |
| 对账与结算确认 | 用量、费用和外部清单是否一致 | 差异识别、处理审批、复核及结算确认单 |
| 运营与管理 | 如何查询、管控和定位异常 | 统计看板、权限、审计、数据质量和运行告警 |

建议先上线用量统计，再上线计费账单，最后完善对账和结算确认。实际支付、自动扣款、税务开票不在本次基础范围内。

## 2. 业务流程与使用角色

### 2.1 端到端流程

**客户调用 → 归属识别 → 用量计量 → 计费资格判断 → 费用计算 → 账单审核发布 → 内外部对账 → 差异处理 → 结算确认。**

| 步骤 | 平台处理 | 产出 |
| --- | --- | --- |
| 1. 鉴权与接入 | 网关独立验证访问；Observer 通过 Host/集群/环境与 Bearer 两类接口确定归属，当前为未实现占位 | 准入结果与归属快照 |
| 2. 计量 | 读取服务返回的用量；必要时估算，无法确认时标记未知 | 不可变的计量明细 |
| 3. 判断 | 按用量来源、完整性、调用结果及合同规则判断能否收费 | 可计费、待核对、不计费三种状态 |
| 4. 计费 | 匹配请求发生时生效的价格，计算费用 | 可追溯的费用明细 |
| 5. 出账 | 按客户和账期汇总，检查异常，审核后发布 | 客户账单 |
| 6. 对账 | 核对内部明细与汇总，并与客户或供应商清单比较 | 对账报告和差异单 |
| 7. 结算确认 | 完成差异处理及必要调整，由授权人员确认金额 | 结算确认单及处理记录 |

“计量”记录消耗，“计费”计算费用，“账单”汇总应收，“对账”验证一致性，“结算确认”确认最终金额。结算确认不表示已经收款。

### 2.2 使用角色

| 角色 | 常用功能 |
| --- | --- |
| 平台管理员 | 接入配置、客户与服务/供应商关联、角色权限、运行监控 |
| 运营人员 | 用量查询、趋势分析、价格维护、计量异常处理 |
| 财务人员 | 账单审核发布、对账、调整审批、结算确认 |
| 客户使用者 | 查看本客户的用量、费用、账单和对账结果，下载清单 |

基础范围采用同一管理门户按角色展示功能，并实施客户数据隔离。价格变更、账单发布和金额调整保留审计记录；金额调整申请与审批由不同人员完成。

## 3. 功能设计与组件划分

### 3.1 接入与归属管理

| 编号 | 功能点 | 功能描述 | 阶段 |
| --- | --- | --- | --- |
| A1 | 客户与服务归属 | Observer 通过两个接口分别解析 Host/固定集群/环境与 Bearer token；目前未实现占位 | 一期 |
| A2 | 服务及模型登记 | 维护服务、模型标识、协议类型和计量规则映射 | 一期 |
| A3 | 采集范围配置 | 默认不采集；配置规则显式启用、POST 与精确路径联合白名单及资源上限；route_name=* 忽略路由名，排除指标/健康检查等普通请求 | 一期 |
| A4 | 接入检查 | 检查可信身份、协议兼容性和用量字段，展示接入状态 | 一期 |
| A5 | API Key 生命周期 | 创建、一次显示、轮换、吊销和禁用密钥，保留操作审计 | 一期 |
| A6 | 网关鉴权 | 通过 Istio/Envoy ext_authz 验证 Key、有效期及访问范围，失败请求不进入模型服务 | 一期 |
| A7 | 访问范围 | 按 API Key 配置允许访问的服务与路由；未明确授权默认拒绝 | 一期 |

当前归属接口已实现并以未实现占位运行：Wasm 临时发送入口 authority 与 Authorization: Bearer token，Observer 固定集群/环境并调用服务/客户 resolver；合法输入的四项 ID 和版本为 null，两类状态为 lookup_not_implemented，原始 usage 保留，identity_status=invalid、usage_eligible=false。真实 HTTP、第三方鉴权和网络缓存未实现；应用维度及 PG 归属读取均已删除。 业务访问继续由已有网关鉴权独立判定，不把统计归属查询放进同步 ext_authz。

真实 Auth、凭证生命周期及访问范围属于独立工作包。本次不建设密钥管理 API，不限制第三方 Key 为自造格式，不返回假客户，不访问 PG。当前接口未实现与真实凭证无效是不同状态；前者不能阻断业务或被计为已知客户。

### 3.2 用量计量与数据管理

| 编号 | 功能点 | 功能描述 | 阶段 |
| --- | --- | --- | --- |
| M1 | 请求采集 | 支持兼容 Chat Completions 的普通 JSON 和 SSE 流式响应，包括工具调用 | 一期 |
| M2 | 用量归一化 | 统一输入、输出、缓存读写、推理等字段，避免包含关系造成重复累计 | 一期 |
| M3 | 缺失用量估算 | 服务有效上报优先；缺失字段采用已验证模型估算或通用估算，否则标记未知 | 一期 |
| M4 | 完整性与异常标记 | 标记断流、缺片、解析超限、身份元数据无效、用量冲突等情况 | 一期 |
| M5 | 去重及统计 | 重复事件不重复计量；按客户、API Key、服务、模型和时间汇总 | 一期 |
| M6 | 明细查询与导出 | 网关在及时收到 Observer Start ACK 时于响应头返回 Observer 生成的 UUIDv4 计量请求 ID；客户按该 ID 精查，按客户/时间限定的 `X-Request-Id` 辅助检索、条件筛选、分页、大范围异步导出 | 一期 |
| M7 | 明细一年保留 | 原始事件按 UTC 开始日分区，在线保留 365 个日期，期限内直接查询 Doris | 一期 |
| M8 | 日汇总 | 集群/环境/客户/API Key/供应商/服务/模型/来源日统计，重放和冲突可重算，独立保留 730 个日期 | 一期 |
| M9 | 月汇总 | 从已发布日汇总生成自然月统计，迟到或冲突触发重算，独立保留 24 个月 | 一期 |
| M10 | 明细归档及外部历史检索 | 仅保留可选设计；归档任务、状态、对象存储及接口另行建设 | 可选扩展 |

来源标识分为：服务上报、已验证模型估算、通用估算、未知。来源与完整性分别展示，估算不冒充服务上报，未知不记为零。

一期仅观察入口直接访问的服务 A 及其最终可见响应，不还原内部 B/C 调用，也不宣称覆盖网关隐藏重试的消耗。客户端每次重新发起的请求分别记录。

计量查询以 Observer 在有效 Start 后生成的 UUIDv4 `logical_request_id` 为主键；ID 不编码日期，统计日期由 `request_started_at_ms` 确定，单 ID 查询覆盖在线日期分区；客户在 ACK 及时到达时可从 `X-Metering-Request-Id` 响应头取得，迟到时此头可缺失；网关可见的 `X-Request-Id` 在事件中名为 `x_request_id`，仅作可选关联字段，可能缺失、重复或保留客户端传值，不作为唯一键或授权凭据。客户查询接口强制按已登录客户隔离，未知用量不显示为零。旁路采集允许丢失，返回了查询 ID 并不保证最终一定有计量记录。

### 3.3 价格与计费管理

| 编号 | 功能点 | 功能描述 | 阶段 |
| --- | --- | --- | --- |
| P1 | 价格目录 | 按模型、计费项维护标准单价，支持客户合同价覆盖标准价 | 二期 |
| P2 | 价格版本 | 配置生效时间、币种和计价单位；已生效价格保留历史，禁止时间区间冲突 | 二期 |
| P3 | 收费规则 | 配置来源准入、成功/失败/取消请求及异常记录的收费处理方式 | 二期 |
| P4 | 费用计算 | 生成请求级费用明细，保留计量依据、单价、规则版本和计算结果 | 二期 |
| P5 | 试算与核验 | 新规则正式生效前试算；账单发布前核验、作废重算草稿，防止重复入账 | 二期 |

基础计价方式为“用量 × 单价”，支持输入、输出及可独立识别的缓存等项目。各收费项必须互斥或明确扣除包含量，不能将已包含在输入/输出中的缓存、推理用量再次相加。无法可靠拆分的计费项进入待核对。

**计算示例：**输入 1,000 token，单价 2 元/百万 token；输出 500 token，单价 8 元/百万 token，则费用为 0.002 + 0.004 = 0.006 元。示例仅说明公式，不代表实际报价。

基础版一个结算主体使用一种币种，不做汇率换算。内部使用定点高精度金额，建议保留 8 位小数；账单汇总后按币种最小单位四舍五入，并保留尾差。最终精度及舍入规则在需求阶段确认。

### 3.4 账单管理

| 编号 | 功能点 | 功能描述 | 阶段 |
| --- | --- | --- | --- |
| B1 | 账期配置 | 基础版按自然月出账，明确结算时区、截止时间及宽限窗口 | 二期 |
| B2 | 账单生成 | 按客户汇总费用，支持按服务/供应商、模型和计费项查看构成 | 二期 |
| B3 | 审核与发布 | 草稿 → 待审核 → 已发布；检查价格缺失、异常用量及数据水位 | 二期 |
| B4 | 查询与下载 | 查看账单概要及关联费用明细，下载标准清单 | 二期 |
| B5 | 调整单 | 与账单发布同在二期交付；发布后通过审批的补收/减免调整单处理迟到数据及差异，保留原账单 | 二期 |

账单展示计费用量、金额、采用的价格、估算占比、未纳入收费的异常记录及当前状态。用量统计总量可能大于计费量，页面提供差额原因。

已发布账单不直接覆盖修改。账单发布后的调整关联原账单、差异原因和审批人，以独立调整单计入后续账单或结算确认单，且只能入账一次。

### 3.5 对账与结算确认

| 编号 | 功能点 | 功能描述 | 阶段 |
| --- | --- | --- | --- |
| R1 | 内部对账 | 核对去重用量与统计汇总、可计费用量与费用明细、费用明细与账单金额 | 三期 |
| R2 | 外部清单导入 | 使用约定模板导入客户或供应商清单，校验字段、账期、币种和重复批次 | 三期 |
| R3 | 自动匹配 | 优先按双方共有请求 ID 匹配；无共同 ID 时按客户、模型、日期等约定粒度汇总比较 | 三期 |
| R4 | 差异分类 | 区分单边缺失、用量差异、价格差异、金额差异和重复记录，支持容差配置 | 三期 |
| R5 | 差异处理 | 待处理 → 核查中 → 待审批 → 已处理 → 已复核；关联证据、责任人，并调用二期已有调整单能力 | 三期 |
| R6 | 结算确认 | 汇总原账单和已批准调整，确认最终金额，生成可导出的结算确认单 | 三期 |

客户应收对账与供应商费用核对分别展示。供应商清单可能包含平台重试或内部调用成本，不要求其直接等于客户应收，也不将供应商费用自动转嫁给客户。基础版不建设供应商应付账本。

无共同请求 ID 时，只能确认汇总差异，不能据此生成逐请求匹配结论。金额和用量容差分别配置，单边缺失不得仅因金额较小而自动消除。

最终结算应满足：差异已关闭，或存在授权人员批准的例外；确认后如需变更，新增调整及确认版本，保留完整历史。全流程不得通过修改原始计量记录来“做平”差异。

### 3.6 运营看板与公共能力

| 编号 | 功能点 | 功能描述 | 阶段 |
| --- | --- | --- | --- |
| O1 | 用量看板 | 请求量、token 趋势、客户/模型排行、成功率及来源分布 | 一期 |
| O2 | 数据质量监控 | 展示独立网关请求基数、已采集请求、未知比例、异常时段和处理延迟 | 一期 |
| O3 | 权限及审计 | 客户数据隔离、角色权限、配置变更审计，后续扩展财务审批审计 | 一期起 |
| O4 | 费用看板 | 预估费用、已出账金额、待核对金额和调整金额 | 二期 |
| O5 | 对账工作台 | 对账批次、差异数量、待办、处理进度及最终确认结果 | 三期 |

## 4. 系统组件及职责

产品按上述模块组织页面；技术实现按以下组件分工，不要求每个组件都独立部署。

| 组件 | 职责 | 主要数据或依赖 |
| --- | --- | --- |
| 网关 ext_authz | 在请求头阶段同步调用 Auth，按结果允许或拒绝业务请求 | Istio/Envoy、Auth gRPC |
| API Key Auth 服务 | 验证密钥、状态、有效期和访问范围，执行独立访问判定，不提供采集补值 | 事实源与凭据方案在真实 Auth 工作包确认 |
| API Key 管理组件 | 创建、一次显示、轮换、吊销、禁用和配置访问范围，记录审计 | Auth 数据源、管理端统一身份，均待独立实施 |
| 网关观察插件 | 在鉴权后补充流式 usage 参数，观察请求与响应，异步发送采集片段 | Istio/Envoy、原 Authorization: Bearer 与入口 Host |
| 计量服务 | 解析协议、提取 usage、估算及标记完整性 | 临时内存处理正文，不持久化正文 |
| 事件与数据处理组件 | 一期采集子项由独立 Doris Consumer 校验、规范化并落库；一期建设独立 Go usage-worker，由每分钟 CronJob 调度，单个发布者从去重请求投影发布日汇总，再按日版本变化生成月汇总；归档不纳入一期 | Kafka、Doris；K8s 调度与发布者保护，无额外 PostgreSQL 汇总库 |
| 计费服务 | 管理价格与规则、判断收费资格、生成费用明细 | 计量结果、价格及规则快照 |
| 账单与对账服务 | 出账、审核、导入匹配、差异处理、调整及结算确认 | 账单、对账批次和审批记录 |
| 管理门户与接口 | 按角色提供查询、配置、导出和工作台 | 统一身份及权限体系 |
| Auth 数据源（待确定） | 独立保存鉴权所需客户/API Key 状态、凭据与管理审计 | 不供 Observer/Consumer 读取归属，不作为本次部署依赖 |
| 账务与配置存储 | 可靠保存价格、账单状态、调整、审批和账务操作审计 | 关系型数据库，是否复用 PostgreSQL 集群在计费阶段确认 |

业务请求走“调用方 → 既有网关 ext_authz → 模型服务”；Auth 是新增的同步鉴权调用，但不转发业务正文，计量服务仍不承担请求转发。计量事件进入数据处理链路后，再由计费及账单组件处理。

Auth 身份存储属于未来独立工作包，不是本次采集事实源；Doris 保存请求级计量明细、日/月汇总以及幂等日期通知、连续消费凭据、任务输入和发布状态。采集与汇总不读取或写入 Auth PostgreSQL，详见[Doris 协调设计](doris-summary-coordination.md)。一期采集子项将固定计量字段作为类型化列写入事件表，规范事件 JSON 仅供冲突核验；事件 ID 标识事件，逻辑请求 ID 标识客户请求，同 ID 不同内容须隔离，Doris Unique Key 必须包含内容摘要以保留冲突变体，并由查询隔离冲突请求。鉴权数据面使用只读数据库账号和有界短 TTL 缓存，吊销传播时间必须验收。账务数据仍使用可靠的关系型存储，是否与 Auth 复用 PostgreSQL 集群须根据权限、容量和故障域另行确认。计费任务以“计量标识 + 有效计费版本”实现幂等，账单仅引用一次有效费用结果；跨组件通过状态核验和重试完成处理，不假设一次写入天然保证全链路一致。

技术基线沿用原方案的 Istio 1.13.5、Kubernetes 1.22。网关插件兼容性及性能需在实际镜像上先行验证，本方案不将原稿中的技术判断视为已经验收的能力。

## 5. 关键业务规则

### 5.1 哪些用量可以收费

| 用量情况 | 建议默认规则 |
| --- | --- |
| 完整、有效的服务上报 | 满足调用结果及合同规则后进入计费 |
| 已验证模型估算 | 合同明确接受估算后才可进入计费，否则待核对 |
| 通用估算 | 展示统计，不自动进入结算 |
| 未知、部分用量、归属不明或字段冲突 | 待核对，不按零用量计费，也不猜测补齐 |
| 平台故障、平台额外重试消耗 | 默认不向客户收费；不可见的消耗仍保持未知 |
| 客户主动取消 | 按合同对已确认消耗计费；原因或消耗不明时待核对 |
| 合法零用量 | 保留零值，按对应规则处理，与未知区分 |

### 5.2 计量与账务各自保留历史

计量结果在首次定稿后不覆盖、不重新分词；正文不持久化，因此无法在事后恢复未采集的 token。消费者在保留窗口内重放已进入 Kafka 的事件属于恢复处理，不等于补采缺失用量。

账务允许在授权审批后产生独立调整单。外部清单、合同或双方确认结果可以作为调整证据，但不能伪装成原请求的实测用量。

### 5.3 出账截止与迟到数据

请求按网关观察到的开始时间归属，用 UTC 存储，出账按预先约定的结算时区划分账期。价格也按请求开始时间选取生效版本，不按入库时间取价。

账期结束后设置可配置的宽限窗口，并检查消费水位、失败计费任务和异常记录。窗口内迟到的已采集事件可以进入草稿账单；窗口结束且账单发布后，再到达的有效记录由二期迟到数据处理流程核验，通过二期调整单入账。三期对账发现的其他差异复用同一调整单能力，不依赖三期上线后才能处理迟到数据。

### 5.4 数据完整性与收费上线条件

原方案采用旁路采集，故障时优先保障业务调用，允许放弃采集，且不设置采集侧落盘和补传队列。这意味着当前架构不能承诺全部实际消耗都可恢复，Kafka 仅保护已经成功入队的数据。

正常运行的请求记录完整率以 99.99% 为待验证目标，使用独立网关指标作为基数；请求有记录并不代表 token 完整。看板同时显示全日、正常和故障时段的结果，不用故障时段剔除后的指标替代全日指标。

正式收费前，需确认可接受的完整性标准、估算规则、异常账单处理方式，并完成至少一个完整账期的模拟出账核验。若客户要求“所有消耗必须可追溯且可恢复”，需另行建设可靠计量源或持久化补传能力，并重新评估架构与工作量。

## 6. 分期建设与上线验收

入口过滤为一期强制约束：只有显式启用的配置规则中同时命中方法和精确路径的请求才采集，一期接入范围支持 `POST /v1/chat/completions`；自定义前缀必须显式登记。普通 GET、指标查询、健康检查、模型列表、OPTIONS 等请求不生成计量 ID、不读取或改写正文、不建立旁路流、不发送 Kafka 计量事件，仅保留本地过滤计数。默认规则为空或关闭时全部忽略，客户端不得控制采集开关；鉴权策略独立于采集策略。目标请求的失败响应和断流仍保留可观察记录，缺少 usage 为未知。完整率独立分母必须限定同方法、路径、路由和观察位置，普通业务流量不计入 Kafka 容量基数。实现遵循[采集开发方案第 2.3 节](gateway-request-collection-implementation.md#23-入口采集过滤强制约束)，上线必须通过同路由推理与普通查询混合测试，确认被过滤请求无旁路消息和 Kafka 计量事件。

| 阶段 | 建设目标 | 交付范围 | 上线验收要点 |
| --- | --- | --- | --- |
| 阶段 0：方案确认与验证 | 明确范围，验证旧环境可落地 | 功能清单、字段与口径、原型、已有鉴权、Bearer/Host 与归属接口验证、网关插件验证、压测计划 | 固定网关可保留 Bearer/Host；过滤器顺序、占位未知状态、旁路资源上限和关闭方式可验证 |
| 一期：可信归属、用量可见 | 阻止匿名调用并查清客户与模型的用量 | 集群/环境/客户/API Key/供应商、鉴权、接入、计量、去重、一年明细、日汇总、月汇总、用量看板、基础权限与监控 | 无效/越权 Key 被拒绝；轮换和吊销正确；可信身份进入计量；JSON/SSE、重放、日/月一致性、迟到/冲突重算、权限隔离与性能通过 |
| 二期：费用可算、账单可出 | 建立收费依据 | 价格版本、计费资格、费用明细、试算、账期、账单审核发布、下载及调整单 | 历史价格可追溯；边界取价与舍入正确；调整单仅入账一次；完成完整账期模拟核验 |
| 三期：差异可处理、金额可确认 | 建立对账闭环 | 内外部对账、差异工作台、差异审批与复核、结算确认；复用二期调整单 | 差异样例识别正确；对账调整可追溯；已发布账单保留；最终金额可复核 |

一期全部子项完成后可先内部上线；一期采集子项完成仅代表明细入库链路可验收，估算、日/月汇总、客户查询与看板仍须按一期其余子项交付；归档不在一期交付或验收范围。二期在一期客户查询基础上交付账单审核发布、账单查询和调整单能力，可完成模拟出账；对正式结算有要求的客户，建议三期验收后再进入常态化收费运营。

性能验收基线沿用原方案目标：正常请求结束后 60 秒内可查常用用量统计；约定查询范围及并发下在线查询 P95 不超过 3 秒；网关观察引入的 P99 首包额外延迟目标不超过 10 毫秒。慢上传、大请求及真实流量混合样本按[采集开发方案第 11.3 节](gateway-request-collection-implementation.md#113-容量与性能验收)单独报告，不得剔除后宣称总体目标达成。新增 Auth 内部处理 P99 目标不超过 20 毫秒、网关 ext_authz 总等待 P99 目标不超过 50 毫秒、硬超时初值 200 毫秒。均需实测确认，不作为已达成承诺。每分钟汇总调度只是队列检查周期，端到端统计延迟还包含排队、消费、重算与发布，不以 CronJob 周期代替性能验收。压测应覆盖实测业务峰值的两倍，以及 Auth/PostgreSQL 故障、密钥吊销传播、慢观察者、长流式响应和 Kafka 故障场景。

## 9. 数据规模、保留与交付前提

设计基线为日均约 5,000 万次调用，平均约 579 次/秒；平均速率不能替代峰值、流式时长及正文大小的实测。需要结合客户真实流量核定网关、计量服务、数据存储及计费批处理资源。

| 数据类型 | 建议保留策略 |
| --- | --- |
| 原始计量事件与拒收诊断 | 按 UTC 日期每日分区，在线一年：365 个日期 |
| 日用量汇总 | 独立保留 730 个 UTC 日期 |
| 月用量汇总 | 独立保留 24 个 UTC 自然月 |
| 可选归档明细 | 一期不实施，后续另行确认期限与查询方式 |
| API Key 主体、版本状态及归属 | 主体存续期加审计要求期限；密钥原文永不保存 |
| 鉴权管理审计 | 建议至少 2 年，最终按安全与合规要求确认 |
| 价格、账单、费用依据、对账及审批记录 | 建议至少 2 年，最终按合同及客户归档要求确认 |
| 请求及响应正文、密钥原文 | 不持久化 |

账单生成时固化可解释收费的费用明细、计量依据快照、价格及规则版本，按账务保留期保存，避免原计量明细到期后无法解释账单。这部分账务归档容量需另行纳入资源测算。两年以上查询、备份恢复及归档要求在需求阶段明确。

后续完整业务方案需客户提供（本次占位不要求真实 Auth/PG）：实际网关镜像和测试环境、客户/API Key 与服务/供应商初始数据、API Key 命名/有效期/轮换/吊销策略、受保护入口清单、PostgreSQL 与 Secret/KMS 基础设施、模型协议与脱敏样例、峰值流量及典型流式时长、收费规则和账期要求、客户/供应商对账样例、基础设施及发布窗口。

阶段 0 的范围确认重点为：客户/API Key 初始迁移、全部受保护路径、上游凭证注入、吊销传播时限、一期模型清单、估算是否允许收费、异常和取消请求如何收费、结算时区与舍入规则、外部对账数据可获得性，以及正式收费是否要求零丢失计量。确认后形成可用于正式报价和验收的工作包清单。
